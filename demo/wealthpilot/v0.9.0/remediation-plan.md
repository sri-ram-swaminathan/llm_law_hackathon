## 1. FR-SUITABILITY-01: Suitability assessment is incomplete · 🔴 blocker

**Legal basis:** MiFID II (Directive 2014/65/EU) Art. 25(2) · Delegated Regulation (EU) 2017/565 Art. 54(2), (5)
**Problem:** the advisor gives personalised recommendations, but the profile doesn't collect the client's **knowledge and experience** of investments or their **ability to bear losses**. Those are the elements required to judge whether advice is suitable.

**Locations**
- `backend/app/models.py:29-40`: `RiskProfile` has age, income, goal, monthly amount, tolerance and horizon only
- `backend/app/schemas.py:19-25`: `ProfileIn`, the same six fields
- `frontend/src/pages/Onboarding.jsx:26-31`: the six onboarding steps
- `backend/app/advisor.py:17-26`: the system prompt doesn't consider suitability

**Required change**
- Add three profile fields:
  - `investment_knowledge`: `none | basic | informed | advanced`
  - `investment_experience_years`: int, 0–50
  - `max_acceptable_loss_pct`: one of 0, 5, 10, 20, 30 or 50
- Add matching onboarding steps (steps 7–9) using the existing step UI pattern.
- Pass the new fields to the advisor. Extend the system prompt so that:
  - it doesn't recommend a product whose risk exceeds the client's tolerance or loss capacity;
  - with `investment_knowledge = none`, it recommends only diversified UCITS ETFs or bond funds;
  - it states in the summary why the advice is suitable.
- Since there are no migrations yet (README "Known limitations"), add the columns as nullable. Treat a profile with any of them missing as incomplete: `POST /api/recommendations` returns 400 *"Complete your risk profile first"*.

**Boundaries:** the files above, plus `backend/app/routers/advice.py` and `backend/tests/`.

**Done when**
- [ ] `PUT /api/profile` accepts and returns the three fields with validation.
- [ ] Onboarding shows 9 steps, and Finish is disabled until all are valid.
- [ ] `POST /api/recommendations` returns 400 for a profile missing any of the new fields.
- [ ] The advisor input JSON contains the three fields (unit test on the prompt builder).
- [ ] Re-assessment marks `FR-SUITABILITY-01` satisfied.

## 2. FR-CIF-STATUS-01 (code part): Product wording contradicts the advice it gives · 🔴 blocker

**Legal basis:** MiFID II Art. 4(1)(4) (definition of investment advice) · Code monétaire et financier L.541-1, L.546-1
**Depends on:** appendix A1. Do this item once the founder confirms the CIF registration (ORIAS number available).
**Problem:** the disclaimer says *"This is not financial advice"*, while the product gives personalised buy/sell recommendations with tickers and percentages. That is investment advice. Once Wealthpilot is a registered CIF, the wording has to state its status, not deny it.

**Locations**
- `backend/app/config.py:10-14`: `DISCLAIMER`
- `backend/app/advisor.py:17-19`: *"you do not present your output as regulated financial advice"*
- `frontend/src/components/Disclaimer.jsx`: renders the disclaimer

**Required change**
- Add the config value `CIF_ORIAS_NUMBER` (env, required in production).
- Replace the disclaimer with a status disclosure:
  - name the CIF status and the ORIAS number;
  - say the advice is non-independent (or independent, per A1);
  - say it's based on the information the client provided;
  - link to the terms.
- Change the system-prompt lines 17–19 so the model presents output as personalised advice under that status and keeps the suitability statement from item 1.

**Boundaries:** the files above.

**Done when**
- [ ] No string in the codebase says "not financial advice".
- [ ] The disclosure shows the ORIAS number on every screen that shows recommendations.
- [ ] Re-assessment marks `FR-CIF-STATUS-01` satisfied, together with A1's evidence.

## 3. FR-SUITABILITY-UPDATE-01: Advice is shown after the client's profile changed · 🟠 high

**Legal basis:** Delegated Regulation (EU) 2017/565 Art. 54(7)
**Problem:** editing the profile overwrites it in place, and the dashboard keeps showing advice generated for the old profile.

**Locations**
- `backend/app/routers/profile.py:12-20`: `upsert_profile`, which has no versioning
- `backend/app/routers/advice.py:31-38`: `latest` returns the last analysis no matter when the profile changed
- `backend/app/models.py:40`: `RiskProfile.updated_at` exists and can be used

**Required change**
- `AnalysisOut` gets `outdated: bool`, which is true when `profile.updated_at > analysis.created_at`.
- The dashboard and Recommendations page show an "Your profile changed. Refresh this analysis before acting on it." banner and hide the recommendations' action buttons while the analysis is outdated.

**Boundaries:** `routers/advice.py`, `schemas.py`, `pages/Dashboard.jsx`, `pages/Recommendations.jsx`.

**Done when**
- [ ] A test shows: update the profile after an analysis → `GET /api/recommendations/latest` returns `outdated: true`.
- [ ] Re-assessment marks `FR-SUITABILITY-UPDATE-01` satisfied.

## 4. GDPR-ERASURE-01: Users can't delete their account · 🟠 high

**Legal basis:** GDPR (Regulation (EU) 2016/679) Art. 17
**Problem:** there is no way to erase an account and its data (`docs/product.md` §10 lists it as a gap).

**Locations**
- `backend/app/routers/auth.py`: has signup, login and me, but no delete
- `backend/app/models.py:20-25`: `User` cascades to profile and holdings only
- `backend/app/models.py:57-64`: `Recommendation` has a plain foreign key to the user, with **no cascade**

**Required change**
- Add `DELETE /api/auth/me`. It requires the password in the body, and returns 204.
  - Deletion **explicitly removes the user's recommendations**, or adds a `recommendations` relationship with `cascade="all, delete-orphan"` on `User`.
  - Then it deletes the user, which cascades to the profile and holdings.
- Add a "Delete my account" action, with an in-page confirmation, in the layout's account menu. Then clear the token and redirect to `/login`.

**Boundaries:** `routers/auth.py`, `models.py`, `schemas.py`, `components/Layout.jsx`, `lib/api.js`, `tests/`.

**Done when**
- [ ] A test shows that after `DELETE /api/auth/me` no rows remain for the user in any table.
- [ ] Re-assessment marks `GDPR-ERASURE-01` satisfied.

## 5. GDPR-SECURITY-01: Tokens can be signed with a public default secret · 🟠 high

**Legal basis:** GDPR Art. 32
**Problem:** if `JWT_SECRET` isn't set, tokens are signed with `"dev-secret-change-me"`. Anyone could forge a session and read another user's financial data.

**Locations**
- `backend/app/config.py:4`

**Required change**
- Remove the default.
- At startup, raise a clear error if `JWT_SECRET` is unset or shorter than 32 bytes, unless `APP_ENV=dev`. In dev mode, generate a random per-process secret and log a warning that doesn't include the value.
- Update `.env.example` and `docker-compose.yml` accordingly.

**Boundaries:** `config.py`, `main.py`, `.env.example`, `docker-compose.yml`, tests.

**Done when**
- [ ] Starting with no secret and `APP_ENV` ≠ `dev` exits with the error message.
- [ ] Re-assessment marks `GDPR-SECURITY-01` satisfied.

## 6. FR-SUITABILITY-REPORT-01: Clients can't see the advice they received · 🟡 medium

**Legal basis:** MiFID II Art. 25(6)
**Problem:** analyses are stored, but only the latest one is shown. Clients can't retrieve the earlier suitability statements given to them.

**Locations**
- `backend/app/routers/advice.py:31-38`: only `latest` exists

**Required change**
- Add `GET /api/recommendations`, which lists the user's analyses (newest first: id, created_at, mode, outdated) and `GET /api/recommendations/{id}`.
- Add a "History" list to the Recommendations page that opens past analyses read-only, with the disclosure from item 2.

**Boundaries:** `routers/advice.py`, `schemas.py`, `pages/Recommendations.jsx`, `lib/api.js`, tests.

**Done when**
- [ ] A test shows two generated analyses are both listed and retrievable.
- [ ] Re-assessment marks `FR-SUITABILITY-REPORT-01` satisfied.
